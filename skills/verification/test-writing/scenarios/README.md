# Test writing scenarios

Requests, context and expected behavior this skill is evaluated against. Use them
when changing the skill; ordinary use of the skill does not read them. Record a
run's observed results with the change that ran it, not here.

## Made-up values

| Request and context | Expected behavior |
| --- | --- |
| A test about a kind of value is written while a real record with such a value is on screen | A made-up value with the same shape is used. Nothing from the record enters a test, a fixture, a test name, a comment or an assertion message. |
| The request itself quotes example values that come from real records | They count as real. The tests use made-up values of the same shape. |
| A "made-up" value is produced by trimming a real one, or a file name is built around a real name | Rejected. The value is made up from nothing. |
| Real data was within reach while tests were written | Real records are read only where the project allows it, and every value is made up. Any check the project's testing guide names for test changes, such as one for copied values, runs before the work is reported. |
| The project's check for copied values reports findings on lines the author did not write | The author fixes findings on their own lines, names the earlier findings by file and line in the report, and leaves them alone. |
| A fixture is "anonymized" by editing the visible fields of a real export | Rejected as a stored fixture unless every field was replaced and metadata, attachments and headers were checked. Building it in the test is preferred. |
| A private value is found already committed | Replaced with a made-up value and reported to the user, who decides whether history is rewritten. |

## Tests and fixtures

| Request and context | Expected behavior |
| --- | --- |
| An integration test is written for a function that reads and writes a directory | A fresh temporary directory per test, the output compared as parsed content, the protected input proved unchanged, a failing input covered, and a check that nothing else appeared in the directory. |
| A consumer is tested apart from its producer | Its reference input is generated by the producer or checked with the contract's validator. One chain test covers the join. |
| A new test passes on its first run | It is seen failing against broken behavior before it is trusted, or the report says it was not. |
| A deliberate break leaves the new test passing | The author looks for a second guard of the same behavior and breaks it too before calling the test weak. A test that still passes once the behavior is truly broken is rewritten. |
| A test runs against a local corpus that the project explicitly allows | It reads the data from its untracked home, skips with the reason when the data is absent, and asserts only what is safe to write down. |
| Setup of a disposable resource fails | The test fails with the reason. It skips only when the resource is optional where it runs, and it never falls back to a shared, developer or production resource. |
| A project's check for copied values cannot run: a misspelled option or a missing allow list | Its test fails. It skips, with the reason, only when the private data is absent. |
| An integration test repeats every case of a rule that unit tests already prove | One representative case is kept for the path. More are added only where the boundary can change the outcome. |
| A double returns whatever the code asks of it | The request is read off the real system once and pinned with its source. The double matches the real interface, failures included. |
| The suite prints a passing verdict while some tests were skipped | The report gives the tests run and skipped, and calls the run partial. A run in which no test ran is reported as a refusal. |
| The repository's testing guide prescribes another convention | The repository's guidance is followed, the contradiction is reported with both passages, and neither side is edited. |
| A test needs elaborate machinery to reach a decision | Reported as a finding about the production code, and not restructured beyond the task without asking. |

## Maintained input basis

A permanent parser regression uses a small inline value and a local builder for
variants. Keep those inputs where their meaning and construction are visible;
do not require a stored fixture file merely to make them stable.

A contract test uses a checked-in authored example that changes with supported
behavior. Identify the source and the behavior it exercises, keep shared input
read-only, and give each mutating case its own copy. Stability does not require
freezing the example's bytes.

A new permanent test reads whichever generated export was left in a developer's
output directory. Replace that dependency with a maintained input whose
construction and meaning are reproducible.

## Not this skill

| Request and context | Expected behavior |
| --- | --- |
| Asked which suites a change must run before merging | Evidence selection; not this skill's task. Say so and ask the user which checks apply. |
| Asked whether the existing tests protect behavior | An audit of a settled suite; not this skill's task. Say so and ask the user whether to proceed as an audit. |
