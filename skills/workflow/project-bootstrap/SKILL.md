# Project bootstrap

Establish enough real project context for the next decision or implementation
task. Installed guidance is only one input: the result needs an understandable
purpose, current scope, policy owner and usable reader routes. Follow the
project's selected document conventions and templates; this skill requires no
particular directory tree, distribution or companion skill.

## Establish the starting point

Resolve the target directory, applicable instructions and authorized scope.
Inspect existing files and Git state before writing. Preserve useful working
agreements, current commitments and unrelated work. A fresh start adopts an
earlier project's technology or obligations only when the user intends it.

Determine whether this is an independent project, a shared policy owner or a
member repository. Reuse accessible shared owners and installations. Members
state their own responsibility and local choices and link the common rules;
they do not need copies of every shared document.

Initialize Git only when included in the task, after checking whether the target
already belongs to a repository. Resolve an unintended nested repository before
creating it. Choose ignore rules for actual expected files, including local
credentials. Remotes, dependencies and runtimes follow the requested setup scope.

## Establish actual context

Use evidence and established decisions to give the repository:

- An overview of its purpose, current responsibility and relevant dependencies.
  An adequate README can own this without a separate design document.
- A policy owner with the known operating facts and adopted constraints needed
  for the work. Follow the project's policy workflow; project-policy is a suitable
  companion when available. Merely linking an installed policy skill does not
  establish the project's policy.
- Explicit consequential unknowns, with what depends on them and when a decision
  is needed. Ask only when the current task needs the answer; proceed with
  unaffected work. An unknown is useful content, not a prompt to invent a choice.

Separate observed implementation, adopted requirements and proposed work.
A local checkout does not establish local-only deployment, synthetic data or
disposable state. A possible future mechanism does not select its technology or
adopt its operational requirements. Keep a requirement in its policy owner and
an implemented mechanism in its overview or design owner. Plans and dated
evidence follow their own homes, outside current-state documentation.

Create only documents with useful content. Apply selected templates without
leaving prompts, invented commands, unsupported guarantees or empty scaffolds.
Preserve adequate existing owners rather than starting a competing policy or
work queue. An existing project's missing context can be filled without
reconstructing its implementation or migrating all its documents.

## Connect the working routes

Merge concise routes into the existing README and agent instructions. Route to
current project policy, overview, selected guidance, document homes and actual
verification commands. Identify local choices, scoped exceptions and unresolved
adoption work. Follow the selected distribution's installation and integrity
procedure when an installation is included; installation alone adopts no rules.
Record adoption explicitly under the task's authority, preserving existing
commitments. Keep imported guidance unchanged and project choices with the project.

Select skills by task, not as a startup reading list. Use the project's planning
route when the setup needs an actionable queue; project-planning is suitable
when available. Establish capture and repair routes required by the adopted
instructions without copying personal preferences into project rules. Guidance
installation does not itself authorize upstream repair or external actions.

For shared projects, verify links from the actual member checkout and workspace
entry points used by agents. Add a workspace hook only within the authorized
setup scope. A missing shared owner blocks only dependent decisions; report the
missing input and continue within known constraints. Do not assume a client will
discover skills in child directories without an explicit route.

## Verify and hand back

Trace the actual entry point to the project's facts and rules, the next task's
guidance and relevant checks. Confirm the policy contains established context,
not only template text or installation links. Check local links, duplicate owners,
unsupported claims and leftover prompts. Run applicable repository checks and
review the intended diff, preserving unrelated work.

Report what was established, its location, checks performed and consequential
open decisions. Distinguish a usable project setup from a working application,
and adopted requirements from verified implementation. Retain a work record only
when the assignment needs evidence beyond the conversation.
