# Choosing the next step

Start with the project's current phase and desired outcome. Select the most
consequential question preventing that outcome, or the smallest useful behavior
whose scope is already understood. Explain what the result makes possible and
why it should come before dependent work.

Choose the kind of work from the uncertainty:

- Use a design exercise when meaning, responsibility or a handoff is unclear.
- Use a bounded experiment when feasibility or a technical assumption is unknown.
- Use implementation when the required behavior and relevant boundaries are
  settled enough to build and check it.

A small manual demonstration can supply evidence before general infrastructure
is justified. Do not expand one uncertain assumption into a platform project or
take an experiment as a commitment to its tested technology.

For the selected action, identify its owner, available inputs, expected result
and completion evidence. Design evidence may trace a normal case and a relevant
failure through the proposed responsibilities; implementation evidence must
observe the required behavior. Select evidence for the actual claim.

Decide now only when an unanswered question blocks this result or delaying it
risks meaningful loss of options, compatibility or retained state. Otherwise
defer it with a revisit condition and the work it affects. A future deployment
choice need not block an independent local experiment; existing data and
compatibility commitments still constrain that experiment.

Check the existing queue before adding work. Refine an adequate item and link
its dependencies. Keep one current next action at its coordination owner and
name any missing prerequisite. Git operations, external jobs, publication and
release follow the project's own authority and workflows; the sequence itself
grants none of them.
