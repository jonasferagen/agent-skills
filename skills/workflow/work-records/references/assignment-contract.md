# The brief-to-report assignment contract

This reference defines what a bounded brief supplies and what its executor
returns. It is reusable work-record guidance. Project owners still decide the
actual authority, obligations, dependencies and acceptance for their work; link
existing contracts rather than replacing them with this reference.

## Bound one assignment

A brief should have one answerable question or deliverable and a scoped
completion condition. One assignment may need several steps, disciplines or
criteria when they contribute to the same result. File length, agent count and
repository count alone do not determine whether to split it.

Split when parts can receive independent dispositions, need different decision
owners or completion evidence, or depend on a decision the earlier part must
first establish. For example, selecting a component's layout and rendering its
finished surfaces can be separate briefs: the selected layout becomes an
identified input to the rendering assignment. Exploring both together is also
valid when the commission explicitly asks for integrated alternatives.

Keep a broad initiative or living specification with its planning or domain
owner. Child briefs link that basis and each name their own question, inputs,
exclusions and return. A parent relationship is context; it does not imply
dependency, automatic completion or permission to start another assignment.
State a real dependency explicitly, including the result required before work.
Reuse common source owners instead of copying the parent into every child.

For an existing broad brief, preserve its revisions and prior evidence. Frame
new bounded assignments for unresolved work; do not retrospectively claim that
old results satisfied completion conditions introduced later.

## What the commissioning owner supplies

Use the project's work-definition shape or existing task system. A bounded plan
item can serve as the brief; a separate commission uses the same requirements.
These contents can be concise prose or links to existing owners, without a
separate template or serialization format.

| Boundary | Make discoverable |
| --- | --- |
| Intent and scope | The bounded question, intended use, deliverable and exclusions |
| Context entry | Project instructions and the owners of relevant methods and constraints |
| Required inputs | Reachable sources and the revisions required; how to find an input whose identity the work must establish |
| Optional context | Background and earlier results, distinguished from required inputs and explicitly excluded results |
| Execution discretion | What the executor can resolve within existing delegation and which choices remain with another owner |
| Evidence and completion | Observable criteria, required checks and what recorded outcome closes the assignment |
| Return | Requested report or existing record, output/evidence home and who assesses the result |

A fresh-context brief needs reachable routes and enough facts to start without
the originating conversation. It need not embed every instruction, command,
source file or procedure. Use stable paths or accessible links instead of
"as discussed" or an unexplained screenshot. Say whether a source is pinned or
must be read in its current adopted form; a link to today's document does not
repin historical evidence.

Separate discovering an input from an unresolved decision needed to choose it.
"Inspect the current fixture and report its identity" is bounded discovery.
"Use whichever prior design we preferred" leaves the basis unknown. The latter
needs a selected source or an explicitly commissioned selection question.

`Workflow: ready`, when used, expresses the commissioning owner's assessment
that the selected assignment has a usable scope and reachable required context.
It does not certify that every prerequisite was verified or grant execution
authority. Record consequential unknowns and the work they block; bounded
discovery of those unknowns can itself be a ready assignment. This is a framing
check, not an additional approval gate or a requirement to migrate old briefs.

## What the executor discovers and preserves

Start at applicable project instructions, then resolve required inputs and
relevant method, process and contract owners. Load what the task needs. The
brief does not override project constraints or make background material a
required input merely by linking it.

Before dependent work, check that required inputs are available and the scope
can produce the requested evidence. Resolve routine implementation choices
within existing delegation. Do not fill a missing selected basis, acceptance
threshold or decision authority from a past chat or your own preference.
Keep prior results excluded when the brief asks for an independent run.

If a consequential prerequisite is missing or owners conflict, identify the
blocked work, the missing answer and who can resolve it. Continue independent
authorized work. Ask for clarification only when needed for the affected work;
neither a template nor missing optional background creates an approval gate.
Report partial or failed execution with its evidence and remaining work. An
explicitly inconclusive investigation can finish when its commissioned question
allows that outcome; incomplete required work cannot be relabelled inconclusive.

## What the executor returns

Use the brief's requested return: a record read as a whole or a concise dated
entry in an existing worklog. A comparison records candidates and comparable
conditions; a transfer identifies delivered revisions, checked properties, gaps
and the receiving owner's next action. Use the project's shape for either.
Record the brief revision and commit actually used, actual inputs and subject,
method, outputs, findings against criteria, checks and limits. State what was
completed, failed or left unresolved and what should happen next.

Keep retained outputs in their selected home and link them. A report can cover
several runs; preserve each run's identity when it affects the findings. Keep
the worklog's chronology and the report's assessment separate without copying
the same narrative into both. Historical reports retain their assessed basis;
later findings go in a new dated entry or report.

Name the acting executor and distinguish their recommendation from the
decision owner's actual disposition. Update the brief's coordination state and
next action only within existing delegation, using its completion condition.
Returning evidence does not commission the next assignment, accept an asset,
or adopt it in a consumer. Existing exchange contracts own those consequences.

## Skill and project boundaries

Work-records owns these record meanings, assignment boundaries and reusable
methods. Concrete authoring shapes belong to the project or its framework. The project owns placement, source access, domain specifications,
planning, actual exchange obligations and decisions. A consumer implements its
own browsing and link resolution. Structural checks verify selected metadata;
they do not establish that an agent can discover, execute or finish the work.

Named-process pages and their format are owned by the project's framework, as
declared in the [extension boundary](extension.md#owned-by-the-project-framework).
No process-format migration, autonomous dispatcher or reporting service is
required to use this guidance.
