# Postgres design scenarios

Requests, context and expected behavior this skill is evaluated against. Use them
when changing the skill; ordinary use of the skill does not read them. Record a
run's observed results with the change that ran it, not here.

## Schema design

| Request and context | Expected behavior |
| --- | --- |
| Create a PostgreSQL entity with no local exceptions | UUID primary key generated by the database; required timestamptz creation and update columns with insertion defaults and an update trigger. |
| Add a simple mutable link | Composite primary key and both bookkeeping timestamps; no redundant UUID needed. |
| Update a row through direct SQL or issue a no-op update | A database trigger updates the modification time and preserves creation time. |
| Use `updated_at` as an optimistic concurrency token | Choose an explicit revision instead; wall-clock time does not guarantee a unique ordered version. |
| Add a foreign key already covered by an index | Review access and column order; avoid a redundant index. |
| Put a stable referenced entity ID inside JSONB | Use a typed foreign-key column unless a concrete payload requirement justifies otherwise; JSON must not become a way around relational integrity. |
| Add a maintained entity whose label and provider URL can change | Stable local key; external identity and display references separate. |
| Add a link that can occur in several capacities | Uniqueness includes the capacity; a surrogate ID alone is insufficient. |
| Add vocabulary codes for cases the domain may need later | Only codes a current domain case needs are added. |
| Create new application tables with no local schema convention | Placed in a named schema that holds one application's or concern's objects, not in `public` or a platform-managed schema. |
| Import a provider ID scoped to an account that is sometimes unknown | Preserve actual scope and case; explicitly choose null equality without treating unknown as a wildcard. |
| Two items share one imported source | Preserve both items; model provenance separately and reject ambiguous capture targets. |
| Replace every boolean with a timestamp, including a required/optional property | Keep the genuine binary property and avoid invented event times. |
| A prerequisite can reopen after completion | Retain its condition and derive whether it currently blocks execution. |
| A relationship has no known start date | Preserve uncertainty; add a validity period only if the domain needs it. |
| Add tracking to existing records and an immutable log | Explain backfill as tracked-since; preserve log-specific timestamp semantics. |
| Set up a development database before a full test suite exists | Isolated storage, applied migrations and useful synthetic data; retained development state is not a reset target, and adding or repurposing an environment is reassessed. Setup and seed mechanics belong to database-migrations. |

## Operations and transactions

| Request and context | Expected behavior |
| --- | --- |
| Retry the same command key with different intent | Surface a conflict; do not duplicate writes or quietly return success. |
| Two transactions insert opposing dependency edges | Assess the shared invariant under concurrency, not just each row in isolation. |
| Delivery succeeds but recording success fails | Account for uncertain delivery during recovery; do not claim exactly-once behavior. |
| A handler catches a failed statement and returns normally | The runner still refuses to commit; the `ROLLBACK` tag that `COMMIT` returns for an aborted transaction is treated as a failure. |
| A capability role is chosen from a request field, or passed as a bind parameter to `SET LOCAL ROLE` | Rejected: the role comes from a closed map in code and is quoted as an identifier; `SET` accepts no parameters. |
| A read-only transaction relies on `SET TRANSACTION READ ONLY` alone | A confirming query follows it; until the first snapshot, the mode can still be switched back. |
| A transaction sets a session-level setting, role, temporary table or advisory lock | `DISCARD ALL` runs before the connection returns to the pool; `RESET ALL` is not accepted as a substitute because it keeps a session role. |
| A rollback or reset fails on a pooled connection | The connection is destroyed rather than returned. |
| A parameterless query string holds two statements | Flagged: the simple protocol runs both; statements go through the extended protocol one at a time. |
| The application sits behind a pooler that assigns connections per transaction | Session-level state is avoided; `SET LOCAL`, transaction-local settings and transaction advisory locks are used. |

## Adoption

| Request and context | Expected behavior |
| --- | --- |
| Adopt into a project using enums, natural keys and command-only access | Evaluate semantics and local conventions; do not require cosmetic migrations or direct table grants. |
| A project's event table keeps `at` beside the bookkeeping columns and rejects mutation | Keep the existing columns and record their local semantics rather than applying a universal update-trigger rule. |
| Fix a query's performance without changing its data model | Use the project's performance guidance; do not expand into a schema redesign. |

## Limits

- The transaction behaviors were checked against PostgreSQL 17 with a
  node-postgres client: the `ROLLBACK` tag after a failed statement, the
  read-only switch window, the `SET LOCAL ROLE $1` syntax error, the two
  statements in one extended-protocol query, and what `DISCARD ALL` and
  `RESET ALL` clear. Behavior behind an external pooler is stated only as a
  consequence of per-transaction connection assignment; other versions were not
  checked.
- Schema cases are author-reviewed against repository files, not live
  databases; no database test or independent agent evaluation has run.
