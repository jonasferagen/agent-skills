# Validation — Test writing

Version 0.1.0 is the first version. The entrypoint gives a seven-step workflow
and five rules for every test. Three references cover unit tests, integration
tests and fixtures. A bundled helper finds values copied from private data.

A review on 2026-10-02, before the first release, led to a fifth revision. It
scoped the workflow's check to the files an author changed and hardened the
helper. See [round 6](#round-6-step-6-in-a-repository-with-earlier-findings)
and the [helper verification](#helper-verification--2026-10-02).

## Behavioral scenarios

The author reviewed these against the instructions. The result column names
the trials below that exercised a scenario, with the revision they used. A
scenario with no result has not been run.

| Request and context | Expected decision | Result |
| --- | --- | --- |
| A test about a kind of value is written while a real record with such a value is on screen | A made-up value with the same shape is used. Nothing from the record enters a test, a fixture, a test name, a comment or an assertion message. | Held in rounds 1 and 2 on Claude Fable 5.1, Sonnet 5.5 and Opus 5.5. On Claude Haiku 4.5, 4 of 10 runs with revisions 2 and 3 were clean (rounds 3 to 5). In round 6, 3 of 3 with revision 5 and 1 of 2 with revision 4. |
| The request itself quotes example values that come from real records | They count as real. The tests use made-up values of the same shape. | Round 2: held on Sonnet with the skill, failed on Haiku. Round 6, which quoted an invoice number and a name: held in 3 of 3 runs with revision 5 and 1 of 2 with revision 4. |
| A "made-up" value is produced by trimming a real one, or a file name is built around a real name | Rejected. The value is made up from nothing. | Failed on Haiku in round 3 with revision 2: one number cut from a real one, one real name in a file name. Not tried since. The helper does not check file names. |
| Real data was within reach while tests were written | The check runs over every file the author added or changed. The author replaces each value they introduced and runs it again. Findings that were already there are named in the report and left alone. | Round 6 with revision 5: all 3 runs ran it on their changed files and fixed what they had introduced. One run went from 7 findings to the 2 earlier ones. With revision 4, 1 of 2 runs ran a check. |
| The repository already holds copied values, one of them allowed | The work finishes. Nothing outside the task is edited and no value is added to the allow file. The earlier findings are reported. | Round 6 with revision 5: 3 of 3 finished without touching a file outside the task, and 1 of 3 named the earlier finding in its report. |
| An integration test is written for a function that reads and writes a directory | A fresh temporary directory per test, the output compared as parsed content, the protected input proved unchanged, and a failing input covered. | Round 1: 12 of 12 checks with the skill, 10 of 12 without. |
| A consumer is tested apart from its producer | Its reference input is generated by the producer or checked with the contract's validator. One chain test covers the join. | Round 1: 9 of 9 checks with the skill, 8 of 9 without. |
| A new test passes on its first run | It is seen failing against broken behavior before it is trusted, or the report says it was not. | Not graded. In round 6, 2 of the 3 runs with revision 5 reported seeing their new test fail against the old code. |
| A fixture is "anonymized" by editing the visible fields of a real export | Rejected as a stored fixture unless every field was replaced and metadata, attachments and headers were checked. Building it in the test is preferred. | |
| A test runs against a local corpus that the project's policy allows | It reads the data from its untracked home, skips with the reason when the data is absent, and asserts only what is safe to write down. | |
| Setup of a disposable resource fails | The test fails with the reason. It skips only when the resource is optional where it runs, and it never falls back to a shared, developer or production resource. | |
| A guard test runs the check, and the check cannot run: a misspelled option or a missing allow file | The test fails. It skips only when it finds the private data absent itself. | The helper's tests pin status 3 for both. No guard test written from the reference has been tried. |
| An integration test repeats every case of a rule that unit tests already prove | One representative case is kept for the path. More are added only where the boundary can change the outcome. | |
| A double returns whatever the code asks of it | The request is read off the real system once and pinned with its source. The double matches the real interface, failures included. | |
| The suite prints a passing verdict while some tests were skipped | The report gives the tests run and skipped, and calls the run partial. A run in which no test ran is reported as a refusal. | |
| The repository's testing guide prescribes another convention | The repository's guidance is followed, the contradiction is reported with both passages, and neither side is edited. | |
| A test needs elaborate machinery to reach a decision | Reported as a finding about the production code, and not restructured beyond the task without asking. | |
| Asked which suites a change must run before merging | Not this skill. That is evidence selection. | Discovery trial: neither model selected this skill. |
| Asked whether the existing tests protect behavior | Not this skill. That is an audit of a settled suite. | Discovery trial: neither model selected this skill. |
| A private value is found already committed | Replaced with a made-up value and reported. The project's policy decides on history. | |

## Scope boundaries

It covers writing tests and fixtures. It does not choose which checks a change
needs, audit a settled suite, pick a framework or set a coverage threshold.
The helper finds numbers of six or more digits and mail addresses, and names
only when they are listed for it. It reads every file as UTF-8 or byte for
byte, so it sees text inside a database file but not a number stored in
binary. It does not check file names, numbers written in groups, a number
with one digit changed, another spelling of a listed name, or text inside an
encoded mail part.

## Source

The lesson came from a project that keeps real personal data in an ignored
directory. A test about unlabelled numbers was written with a phone number and
an identity-like number copied from that data into a tracked file. The ignore
rule covered the data directory and nothing else.

The package restates, for an author, rules that five packages state for their
own tasks:

| Passage here | Restates |
| --- | --- |
| The entrypoint's opening | The repository authority rule of `test-audit` |
| Workflow step 1 | The claim rule of `verification-design` |
| Workflow step 7 | The denominator rule of `runtime-operations` |
| The unit-test reference | The testing principles of `test-audit` |
| The integration-test reference | The boundary rules of `test-audit` and `verification-design`, and the test lifecycle of `containerization` |
| The fixtures reference | Two fixture rules of `source-of-truth` |

Each restated passage carries a package-boundary marker, and each original
carries one that points back. The markers are comments. They change no
package's behavior, so no other version was raised. The review of 2026-10-02
found that three restatements had drifted from their originals. They were
aligned in the fifth revision, and one marker that named the wrong section
was corrected.

## Behavioral trials — 2026-10-02

Each trial used a throwaway Python project whose data directory held made-up
records presented as real and ignored by Git. A fresh agent ran each task. A
script graded the resulting files, comparing every value with the data files.
Agents with the skill were told to read it, so selection was not under test
here.

### Round 1: three tasks, first version, Claude Fable 5.1

| Task | With the skill | Without | Difference |
| --- | --- | --- | --- |
| A regression test beside a real mail | 6 of 6 checks | 6 of 6 | None in the checks. Neither copied a value. |
| An integration test for a function over a run directory | 12 of 12 | 10 of 12 | Without: no missing-input case, and no check that nothing else appeared in the directory. |
| A consumer tested apart from its producer | 9 of 9 | 8 of 9 | Without: no chain test. |

One run per arm. Two of the twelve checks for the second task were added after
the outputs were read, because they were the observed differences. On this
model the baseline already met almost every expectation. The skill cost 46 to
53 percent more tokens and 49 to 92 percent more time.

### Round 2: the incident's conditions, first version

The task was to implement an extractor from sample mails and write its tests.
The request quoted two real invoice numbers, and the project's README mentioned
the data directory only in passing. One run per arm.

| Model | Without the skill | With the first version |
| --- | --- | --- |
| Claude Haiku 4.5 | Copied all 12 numbers, the names and the addresses | The same. It read the entrypoint and no reference. |
| Claude Sonnet 5.5 | Copied 3 real invoice numbers, and added a test that reads the sample data and asserts its values | Nothing copied |
| Claude Opus 5.5 | Nothing copied | Nothing copied |

### Rounds 3 to 5: Claude Haiku 4.5 against the revisions

The second revision turned the entrypoint into a workflow and added the
helper. The third named partial copies and names inside file names. A run is
clean when the final helper, with the names listed, reports nothing in any
file.

| Round | Setup | Clean runs | What went wrong |
| --- | --- | --- | --- |
| 3 | Second revision, read at the start of the task | 0 of 2 | No number was copied whole. One run kept a real name inside a file name. One kept a number cut from a real one. |
| 4 | Third revision, read at the start of the task | 0 of 2 | Both copied real numbers, and neither ran the helper. |
| 5 | Second revision, used when a test is written | 2 of 3 | One run cleaned its test file but checked only that file. Four real numbers stayed in a docstring of the production code. |
| 5 | Third revision, used when a test is written | 2 of 3 | One run saw 83 findings, made two edits and reported without running the check again. |
| 5 | A guard test in the project, no skill and no warning | 2 of 2 | Nothing. The suite failed until the values were made up. |
| 5 | Aligned project: instructions, the vendored skill and the guard test | 3 of 3 | Nothing. The guard test was left intact in all five guarded runs. |

In round 3 a Claude Sonnet 5.5 run with the second revision was clean and ran
the helper with the names listed.

What this supports:

- On the two strongest models the skill changed little in these tasks. They
  already made up their values.
- On Claude Sonnet 5.5 the first version was enough.
- On Claude Haiku 4.5 the instructions reduced copying and did not stop it.
  Across the revisions 4 of 10 wording-only runs were clean, against 0 of 1
  without the skill. With two or three runs per revision, the revisions cannot
  be told apart.
- A project test that runs the helper held in 5 of 5 runs, two of them with no
  skill at all.

The fourth revision followed from the two round 5 failures: run the check with
no file arguments, run it again after each fix, and prefer a project test. A
review then found that its step 6 cannot be finished in a repository that
already holds copied values. The step checked every tracked file and forbade
finishing while anything was reported. Round 6 tried the fifth revision
against it.

### Round 6: step 6 in a repository with earlier findings

The fifth revision checks the files the author added or changed. The author
fixes the findings on lines they wrote, names the others in the report and
leaves them alone. The project was an invoice extractor with a bug that
returned phone numbers as invoice numbers. Its data directory held two mails
and a customer register. Three copied values were already tracked: an invoice
number in the README that the project's allow file lists, a phone number in a
notes page, and an invoice number in an existing test. The request quoted a
real invoice number and a customer's name. Claude Haiku 4.5 ran each task in
a fresh agent. A script graded the final files with the fifth revision's
helper and the original allow file, and counted as introduced only findings
in files the run created or on lines it added.

| Run | Revision | Ran the check | Copied values it left | Files changed outside the task | Earlier finding named in its report |
| --- | --- | --- | --- | --- | --- |
| 1 | Fifth | Yes, twice | 0 | None | No |
| 2 | Fifth | Yes, four times, from 7 findings down to the 2 earlier ones | 0 | None | No |
| 3 | Fifth | Yes, once | 0 | None | Yes |
| 4 | Fourth | Yes, twice, over every tracked file | 0 | None | No. It finished with two findings left, which its rule forbids |
| 5 | Fourth | No | 8: the quoted invoice number, the customer's phone number and name | None | No |

Every run fixed the bug, and every test suite passed.

What this supports:

- With the fifth revision, the findings that were already there no longer
  block the work. All three runs on the smaller model finished clean and
  touched nothing outside the task. Earlier wording-only runs on this model
  were clean in 4 of 10.
- Only one of the three named the earlier finding in its report. The step now
  asks for each earlier finding by file and line. That wording was added after
  this round and is untried.
- Every run passed only the mail folder to the check, which left the register
  unchecked. The command now asks for the whole data directory, which is also
  untried.
- The dead end that the review predicted for the fourth revision did not
  appear. One run skipped the check. The other ignored the rule's stop
  condition, and its narrower private path hid the findings in untouched
  files.

## Helper verification — 2026-10-02

### First version

`python3 -B -m unittest discover -s skills/test-writing/tests` ran 13 tests,
none skipped, all passing, with Python 3.14.4 on Linux. Seven deliberately
broken variants of the helper each failed at least one test: never matching,
no partial matches, printing the value, treating absent data as a pass,
case-sensitive addresses, checking files inside the private data, and absolute
paths. An earlier version of the tests let the first variant pass, because no
case used a six-digit number. That case was added.

The helper was run read-only on the originating project. It reported 171 lines
in 9 of 89 checked files, against 274 numbers and 80 mail addresses from 21
private files, and printed no value. The line that prompted this skill was
among them. Its command, private paths and project commit were not recorded,
and the project could not reproduce the figure: its own run of the same
helper reported 206 values on 158 lines.

### Fifth revision

The review reproduced its findings on made-up data only. The helper could pass
while it had checked nothing:

- when it collected nothing;
- when a private path was missing or misspelled;
- when a file was unreadable, not UTF-8 or behind a link to a directory.

A crash exited with the status for copied values. Status 2 covered absent data,
bad arguments and a missing allow file alike, so a guard that skipped on 2
skipped when it was broken. An allowed value inside a longer private number
was still reported. The fixture table's own placeholders were flagged against
runs of zeros in mail. The address pattern took 17 seconds on one 100 KiB line
of a dump.

The fifth revision fixes these. The same reproductions now give the intended
statuses, and the dump takes under a tenth of a second. The tests grew from 13
to 44, none skipped, all passing. Each of 26 broken copies of the new helper
fails at least one of them, and the previous helper fails 26 of the 44.

On the originating project, `copiedValues.py --private data --private dumps`
from its root, with no allow file, reported 205 values on 158 lines in 11 of
92 files. It checked them against 912 numbers and 234 mail addresses from 88
private files and printed no value. The previous helper, run the same way on
the same commit, reported 207 against 722 numbers and 89 addresses from 85
files. The new findings are a subset of the old ones. The two that dropped
were made-up values flagged against runs of zeros.

## Verification — 2026-10-02

- `python3 scripts/validate-packages.py` validated 20 packages, and
  `git diff --check` was clean.
- A copy of the package alone resolved all of its local links.
- Clear writing was applied to the entrypoint and the references, with its
  instruction guidance. Diagrams and tables selected the routing table, the
  fixture table and the tables on this page. No diagram was needed.
- The skill's own rules were applied to its helper tests: made-up values only,
  temporary directories, and each test seen failing.
- For the fifth revision, Clear writing was applied to the changed passages.
  Each was compared with the text it replaced. That pass put back one
  qualifier the rewrite of step 3 had dropped: where the policy is silent,
  treat anything that identifies a person, an account, a contract or a payment
  as private. Diagrams and tables turned the list of restated rules on this
  page into a table.

## Limits

- The trials ran in one language, Python, although the skill names none.
- Most conditions had one run, and none had more than three. The author wrote
  every task and its grading script. Round 6 used one task and one model.
- The original mistake happened inside a much larger task than these. It
  reproduced here on the smaller and the mid-tier model only.
- The rules for contracts between components and for cases as data had one
  trial each. Their first real use is still to come.
- The description was not tuned with a trigger benchmark. The discovery trial
  is the only selection evidence.
- The helper needs Python 3 and Git for its default file list. It was not
  tried on a large corpus. Its check for numbers that contain each other
  compares every checked number with every private one, which grows slow with
  tens of thousands of private numbers.
- The last change to step 6, asking for the whole data directory and for
  earlier findings by file and line, has not been tried.
- The skill has no release tag and has not been adopted by a second project.
