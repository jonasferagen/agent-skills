A proposed `/health` response can expose the PID after startup validation, while `status` also reports the selected checkout/revision and service identity. It must never kill the unrelated port owner. Bound startup and shutdown, clean up only the failed attempt, and report cleanup failure separately from the original failure. Select the process manager only in the subsequent implementation design after these outcomes are agreed. 4. **Design the build consumer against that contract.** The build-script maintainer should give the client bounded connection and total wait times, a finite retry rule, and an actionable nonzero exit when the intended service is absent, not ready, or has the wrong identity. A starting concrete budget for discussion is a 10-second readiness deadline, at most 1 second for each HTTP attempt, and retries every 250 milliseconds; these are proposed values, not verified guarantees. Builds must not hang, silently accept any HTTP 200, or substitute a stale success signal. Define whether absence stops the build or disables an optional step from the actual build dependency. If the status is a required build gate, propose failure before the dependent build action. The service/runtime owner owns lifecycle evidence; the build-script maintainer owns consumer evidence. Each check must name its command, environment, asserted outcome, and actual case count. A run with no cases is not a pass.

   - Exercise the real HTTP operation: expected path/body/status, not-ready response, intended identity, and any adopted rejection/compatibility cases. A handler-only test cannot establish the public HTTP contract.
   - Start the named service, verify readiness belongs to that process and selected checkout, let the launching command exit, and probe again. Verify whatever logout/reboot survival was actually adopted with that chosen runtime; caller exit alone does not prove it.
   - Put a synthetic unrelated listener on the selected port, including one returning a successful health-looking response. Startup must fail, must not claim that listener as its service, and must leave the unrelated process alive. Exercise startup/readiness timeout and failed cleanup separately.
   - Stop and restart only the intended service/process group. Confirm shutdown releases its resources within the adopted budget and that restart exposes the intended changed checkout/settings. Exercise concurrent/repeated control calls if they are supported.
   - Terminate the service after it becomes ready and verify status, logs, and the build client detect the loss. Exercise the adopted restart rule, including repeated failure and exhaustion; verify recovery does not continue indefinitely or launch duplicates.
   - Run the actual build consumer against ready, missing, delayed, hung, wrong-unit, and failed-service cases. Assert bounded completion, exit code, useful diagnosis, and whether the dependent build action ran. Include the expected concurrent build demand before deciding whether the current serving mechanism needs to change.
   - Confirm loopback-only binding, intended local origin handling where relevant, and no unintended external action. Check log behavior under the agreed unattended interval/failure volume.

A syntax check, plan, or successful request alone cannot meet that gate. Hosting, a database, secrets, extra transports, a generalized monitoring system, and multi-user access stay deferred.
