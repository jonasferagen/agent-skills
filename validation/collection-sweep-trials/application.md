### application-read

Request:

Design a small read-only operation that takes already-loaded invoice rows and returns a total. Give the boundary and a minimal pure-function interface in your answer. Inputs are supplied by the caller; no provider or storage is involved.

Raw answer:

Use one pure function that sums the amounts in the caller's already-loaded rows.
It consumes those rows, returns the total and changes no caller-owned data. It
needs no provider, storage, job identity, retained receipt or framework.

For a concrete minimal interface, assume the existing row contract supplies a
validated integer `amount_minor` in one currency:

```python
def invoice_total(rows):
    return sum(row.amount_minor for row in rows)
```

This is an illustrative proposal, not implemented code. The operation returns
an integer in the same minor unit; empty input returns zero. It includes each
supplied row once, preserving allowed credits rather than clamping negative
amounts. Parsing, currency selection and determining each invoice amount remain
with the caller's existing input/domain owner. If those assumptions do not match
the project's row contract, use its existing exact money representation instead;
do not sum incompatible currencies or introduce floating-point rounding.

The useful boundary traces are two rows totaling their exact amounts, empty rows,
and a disallowed mixed-currency input caught at its owning input boundary. No
I/O failure or publication recovery exists in this operation. Implementation can
start with the function once the row and money contract is confirmed. These are
design traces; no runtime tests or repository documentation were added.

### application-status

Request:

Sketch an operation to look up the current status of a known external job and return it to a caller. Use the supplied contract and keep its existing no-retention behavior. This is design only.

Raw answer:

Use a read-only function with the known provider job identity and a narrowly
injected status reader:

```text
lookup_job_status(job_id, status_reader) -> queued | running | done | failed
```

The reader adapter performs the supplied `GET /jobs/<id>` operation and maps its
response to one of the four supplied states. The application returns that state
to the caller. It does not submit another job, download an output, write a run
record or retain the provider response. Ordinary startup code can supply an
existing authenticated reader and own its lifetime; no worker, registry or
service framework is needed for this sketch.

A `failed` job state is a successful status observation of a failed job. A timeout,
transport error or unrecognized response is a lookup failure and must remain
distinct; it must not be represented as queued, failed or an absent job. The
supplied contract does not establish missing-job responses, wire field names,
authentication details, deadlines or retry limits. Preserve those as adapter
implementation prerequisites rather than inventing provider capabilities.

Trace one successful lookup returning running, a provider result returning
failed, and a failed read whose error reaches the caller without any retained
response. Safe repeated reads do not imply permission to repeat job submission.
Any bounded read retry would follow the existing read contract and deadline;
this sketch adds no hidden retries or live calls.

The design uses the project-supplied contract. No provider identity or current
official documentation is available here, so independent contract verification
remains an implementation prerequisite. Local doubles could later check mapping
and failure handling, but could not verify provider behavior. This is design only;
no provider request, service call or runtime check was made.

### application-records

Request:

Design the run record for a local import attempt that writes an artifact then records publication. A previous attempt was interrupted after writing temporary bytes and currently says running. Explain identity, recovery and technical completion; no runtime code or new service framework is requested.

Raw answer:

Treat the retained run record as evidence of an attempt, its consumed input and
the artifact it actually published. The interrupted record saying running is
not technical success or a confirmed failure: reconcile its outcome before
claiming completion.

The following is a proposed minimal record, sized to the local import and
publication recovery question; it is not a common job framework.

| Record part | Meaning |
| --- | --- |
| attempt_id, prior_attempt_id when relevant | Identifies this execution separately from earlier attempts; never overwrites their history |
| input_revision and approved input identities | Identifies the exact input set; where byte identity matters, retain SHA-256 and byte length for bytes actually consumed, with paths relative to an identified root only when policy permits |
| relevant configuration and tool versions | Explains decisions affecting output; omit secrets and prohibited input content |
| planned artifact_id and owned scratch identity | Associates scratch/final candidates with this attempt before writing; scratch is not a published result |
| artifact-write and publication stages | Each has not-started/running/passed/failed state and relevant timestamps; an interrupted running stage is unresolved until checked |
| published artifact identity | Final artifact_id, approved location, actual byte digest/length and required completeness evidence |
| permitted diagnostics | Bounded reason codes, affected stage and safe aggregate context; arbitrary local input values, secret-bearing paths and raw payload/error dumps are not retained |
| technical outcome and acceptance | Technical outcome records completed or unresolved/failed work; receiver acceptance is a separate fact, unknown unless actually reported |

Keep input revision, attempt identity and artifact identity separate. A new attempt
may consume the same revision but preserves the prior attempt. Reusing an input
revision with changed bytes is a conflict, not a silent refresh of its hash.
Hashing parsed/canonical content needs its own representation identity; a digest
does not establish provenance or suitability. If a stable input is required,
capture a consistent snapshot or control its writers rather than assuming that
before/after hashes prove it never changed.

Use a single writer per attempt/output identity for the first implementation,
enforced by the existing local locking/ownership mechanism. If none exists, that
is an implementation prerequisite; a record rename alone does not serialize
competing writers.

Choose publication through the retained record: readers discover artifacts only
from a completed publication record, never from scratch or an unreferenced final
file. Persist the attempt intent and planned artifact identity first. Write to
owned staging, check the required output completeness, then place a verified
artifact at its immutable final identity. Publish the record referencing that
artifact and its checked byte identity last. A temporary sibling record followed
by replacement prevents ordinary readers from seeing a partial record, but does
not make artifact placement and record replacement one transaction or promise
power-loss durability. This design therefore needs the recovery rule below.

For the supplied interrupted attempt:

1. Confirm the prior writer has stopped and acquire its local ownership control.
   Preserve the running record as an unresolved observation while investigating.
2. Inspect only the scratch/final candidates associated with its planned artifact
   identity. Confirm input/configuration identity before continuing under the
   same attempt; changed input requires a new revision/attempt.
3. Temporary bytes alone prove neither completeness nor publication. If they are
   complete and their identities are established, the owned attempt may finish
   artifact placement and record publication. If they are partial or cannot be
   verified, keep the failure/uncertainty explicit, handle only owned scratch
   under retention policy and start a linked new attempt if needed.
4. If a verified final artifact already exists but record publication was
   interrupted, reconcile that exact artifact into the record without importing
   again or overwriting another candidate. If record and artifact disagree,
   report the conflict; do not bless either by recomputing an expected hash.

Technical completion requires the final artifact, its required completeness and
identity checks, and the authoritative publication record to agree. Successful
writing of temporary bytes is insufficient. Receiver approval of artifact
quality remains separate from this technical result, and deletion/retention
follows the existing project policy rather than completion alone.

Before implementation can claim these guarantees, exercise interruption after
scratch writing and after final artifact placement but before record publication,
then verify recovery without duplicate/conflicting publication. Also check changed
input under a reused revision and prohibited-content exclusion from diagnostics.
Those are proposed checks, not tests run here. No runtime code, provider call,
new service framework or adopted retention policy was created.
