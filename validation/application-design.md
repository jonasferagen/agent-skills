# Application design validation

Status: initial draft package, bounded trials complete, 3 October 2026. No release
tag or consumer adoption is claimed.

## Intended behavior

| Request | Behavior to inspect |
| --- | --- |
| Design one external generation operation | Reach integration guidance; preserve uncertain submission, retained outputs and the provider's actual capabilities |
| Design a local candidate-receipt operation | Own publication and acknowledgement without introducing provider mechanics or creative acceptance |
| Change one sentence literally | Make the edit without an application-design pass |

Evaluate the initial collection through the
[routing trial method](discovery.md#routing-trial-method). These are document
trials in isolated fixtures. They cannot establish working adapters, storage
durability, provider retry guarantees, native host discovery or broad reliability.

## Observations and review

| Case | Observed route and outcome | Parent assessment |
| --- | --- | --- |
| Provider | Application collection → application-design → external integrations; no foundation or source-maintenance reads | Preserved direct audio response, unknown submission outcome, no automatic resubmission, retained bytes and separate Assets acceptance |
| Receipt | Application-design plus foundation contract, status and authoring routes; no external-integration reference | Preserved complete-set verification, publication before acknowledgement, repeat receipt, conflict and local writer exclusion; no provider/job framework introduced |
| Wording | Project instructions and foundation entry; application collection unopened | Exact requested edit; architecture and remaining README bytes preserved |

The [provider proposal](application-foundation-trial/provider/design.md) maps a
synthetic ElevenLabs sound request to a local operation, provider adapter and
attempt repository. It distinguishes a retained local submission marker from
proof that the provider received the request. Lookup, cancellation, idempotency
and recovery of lost audio remain unverified. The next increment is local
preparation, persistence and a fake direct-response dependency; it does not claim
generation or live-provider readiness. Real brief, model/encoding choices,
access, data and spending scope remain prerequisites. Its storage and durability
mechanisms are proposals requiring runtime evidence.

The [receipt proposal](application-foundation-trial/receipt/design.md) uses a local
operation and filesystem collaborator. It chooses a single writer and publication
of bytes with receipt metadata, and traces loss of the acknowledgement response.
It deliberately defers creative review, selection and general storage. Its pair
of candidate/attempt identities is explicitly a proposed interpretation needing
confirmation, not a newly adopted handoff meaning. Input-root resolution also
needs an exact implementation contract: the example's proposed prefix translation
is not a verified path resolver. The two synthetic payload lengths and hashes
were mechanically checked by the evaluator; no receipt or crash-recovery test ran.

Both designs retain unresolved implementation choices and offer checks at the
actual filesystem/process or provider boundaries. The parent found no material
violation of the supplied design constraints requiring a skill change. These
proposals are retained as evidence, not promoted into live Forge architecture.

These are displayed-file subtotals from the read logs, not total model context
or token use. They exclude mechanical rereads and conversation instructions.
Each evaluator reported no truncated content. The differently grouped subtotals
are labeled rather than treated as a controlled efficiency comparison.

The receipt evaluator's additional contract route was defensible because it was
applying handoff obligations. Its authoring chain followed that collection's
instructions; those reads do not establish a mandatory dependency of the new
core. The wording evaluator called the foundation entry useful, but the parent
found it unnecessary for an exact replacement under the already sufficient local
hook. Neither observation establishes a new application-design routing defect.
No source-maintenance reading or installation workflow was activated. The provider
trial exercised the core without reading its available companion collection.

Remaining coverage: no absent-foundation discovery trial, language-specific
implementation, pure read-only application operation, HTTP/MCP adapter, second
provider or native host discovery was exercised. There was no no-skill baseline,
repeated reliability measurement or collection release self-conformance review.
One successful route per case establishes the observed behavior only.

## Authoring and checks

Skill-creator informed the single core workflow and conditional reference.
Clear-writing and its instruction guidance informed conditions, proposal status
and scoped requirements. Diagrams-and-tables informed the compact responsibility
and evidence tables; no diagram source was introduced. Verification-design and
the repository routing method informed design trials rather than tests that only
match instruction wording. Pattern-capture's ownership test kept provider facts
in trial evidence and language/runtime rules in existing packages.

The installation boundary uses the existing package rules: all required links are
internal; companions are independently pinned through project instructions. No
validator, runtime helper, release tag or installed consumer changed. The generic
collection release-name convention now covers both collections, and the release
self-conformance route includes application designs when a collection produces
them.

Checks performed: repository package validation passed for 26 skills in two
collections; the system skill validator passed application-design; three installed
candidate copies matched the source; fixture integrity preserved all supplied
inputs except the exact authorized README replacement. Final local links and
heading checks passed for 132 local links, including 18 anchored targets across
changed Markdown. `git diff --check` passed. No helper behavior changed, so no
runtime test suite was added or run.
