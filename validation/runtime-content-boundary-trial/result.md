The same renderer environment could support selected report collections if it can load a collection independently of its source location and keep preparation writes outside the authored files. The README's read-only volume plus config file is a proposal for that separation. It has not selected a delivery format, a compatibility contract or runtime packaging. The foundation keeps this work within local exploration: Research owns report definitions, Render owns renderer source and execution, and reviewers accept findings.

The README describes the current flow. Research authors title/layout files, SQL transforms and Python extension scripts in `definitions/`. Render's `renderer.py` branches on report ID, reads those files and writes compiled templates beside them. Reports A and B already use this arrangement according to the README. A saved title edit reaches the next render without a renderer change; an unsupported chart type requires changing `renderer.py`. Selected output and logs are retained separately from disposable rendered pages. A completed render and a reviewer's acceptance remain separate outcomes. These are documented behavior claims, not observations from running the renderer in this exercise.

Four things need separate treatment in the proposed arrangement. Renderer code supplies the supported behavior and execution environment. Research's collection supplies authored definitions, including executable SQL and Python. Configuration selects the collection and report for a run; selecting a particular revision is an additional design choice. Compiled templates and other preparation state are generated material, whose write location and reuse rules belong with Render's preparation behavior. Authored definitions and selected evidence must remain recoverable; disposable pages and generated preparation state do not replace them. Moving definitions to a read-only volume directly conflicts with today's source-adjacent compilation, so preparation writes need a writable location outside that volume.

Collection selection needs to reach every relevant read, including transforms, extensions and their resources. Merely passing a root directory will not remove coupling if a report-ID branch still assumes particular paths or capabilities. The design should distinguish selecting content from selecting runtime behavior. Research can revise a title within supported behavior. A new chart capability still needs Render work unless an already-supported extension mechanism can express it; the README does not establish such a mechanism. The exact authorship of the selection configuration is not recorded and should be agreed without transferring ownership of definitions or renderer code.

Compatibility is consequential because the collection contains executable material. SQL transforms and Python scripts currently run with the renderer process's privileges. Read-only source storage prevents those source writes but does not establish execution isolation. Render needs to know which layouts, chart types, transforms, script interfaces and dependencies it can consume, and how it reports a missing or incompatible requirement. Research supplies definitions consistent with that agreement; Render diagnoses loading, preparation and execution failures; reviewers still decide whether findings are accepted. A precise compatibility format can remain open during this design review, but it needs an answer before relying on separately delivered collections.

Direct use of authored files preserves the current short edit-to-render cycle and may be enough for local exploration. An assembled delivery could instead select a stable revision and include prepared resources, but it adds preparation ownership, source provenance and invalidation questions. If a title or shared definition changes, the design must say which prepared resources become stale and which later render uses the change. In either option, a failed load or preparation should leave the authored collection and previously retained evidence intact, with enough retained run information to associate an outcome with the selected content and renderer behavior. These are proposed expectations, not verified guarantees. Repository separation, delivery format and renderer packaging are separate choices; the proposed split does not itself require a container or another repository.

The expected result is a concrete decision about whether direct loading can support this local workflow, together with the necessary source/preparation boundary and the smallest unresolved compatibility obligations. The walkthrough succeeds as design evidence if all traced reads follow the selected collection, preparation avoids its authored files, content-only changes have a clear freshness rule, and runtime-dependent changes have a clear Render owner. If this cannot be traced without hidden assumptions, record those assumptions as the next design work. Runtime feasibility and successful recovery would still need a separately scoped implementation experiment. Packaging remains open until the workflow creates a reason to choose it; exact delivery and compatibility formats need revisiting before independent delivery is adopted.
