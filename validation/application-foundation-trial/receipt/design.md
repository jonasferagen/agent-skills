# Assets receipt command proposal

Status: proposed design, 2026-10-03. No command is implemented or executed. The supplied [handoff terms](handoff.md) govern custody; this proposal chooses internal mechanisms within the scope of [project.md](project.md).

Implement one local operation, `receiveCandidateSet(delivery)`, exposed by an Assets command. It receives the complete expected output set, retains and verifies its bytes, and returns a durable receipt. Tools uses that receipt to establish transfer of custody. Creative review, selection, general revision machinery, database storage, Game adoption and provider execution remain outside this operation.

## Boundary and responsibilities

The command adapter parses the supplied JSON, accepts explicitly configured input and retained-output roots, invokes the operation and writes its acknowledgement to stdout. Diagnostics and non-success outcomes go to stderr with a nonzero exit status. The acknowledgement is the stored receipt, not a newly generated success statement. Failure to write stdout cannot undo committed receipt.

The receipt operation owns complete-set validation, repeat/conflict decisions and the sequence from acquisition to publication. It requires nonempty candidate and attempt identities, a nonempty output list, unique output names, nonnegative integer lengths and valid SHA-256 values. Names must be safe single filenames; identities must never become raw filesystem paths. Reject absolute retrieval paths, traversal and symlink escapes. Source locations resolve beneath the configured input root; the command must not interpret them as network URLs. For the sample, choose the fixture's `inputs/` as that root and translate its `inputs/shape.bin` and `inputs/surface.bin` references relative to it. Reject extra or ambiguous fields if their meaning would affect receipt; do not silently invent output membership.

A cohesive local storage collaborator owns safe source opening, streamed copy and hashing, lock acquisition, private staging, durable file writes, final publication and reading existing receipts. It reports typed facts and failures to the operation; it does not decide whether a mismatch counts as success or whether a candidate is creatively acceptable. Its boundary exists because filesystem errors, locking and publication determine observable correctness. No factory, registry, job scheduler or dependency injection framework is required.

Ordinary command startup validates configuration, constructs the operation and storage collaborator, and owns their lifetime. The retained root is explicit configuration, not inferred from the input directory. Its exact path is not supplied in this fixture. Use a single local filesystem with reliable exclusive process locking, atomic same-filesystem directory rename and file/directory synchronization. Select the runtime and verify those facilities before claiming crash durability. Network filesystems and multiple hosts are excluded from the first implementation.

## Identity and durable contents

Propose the exact `(candidate_id, attempt_id)` pair as the receipt key. A canonical expected set contains each output's name, length and SHA-256, sorted by name. Ordering and retrieval location are transport details, so relocating unchanged bytes does not create a new candidate result. Persist the exact identities and canonical set, and derive a safe directory key from their unambiguous encoding; compare stored identities as well as the directory key. Cross-attempt deduplication and candidate revision semantics are unspecified and deferred. This pair-key choice is a proposed local interpretation to confirm when implementing, not a new handoff obligation.

One final directory contains both all retained output files and `receipt.json`. The receipt records its format version, candidate and attempt identities, each output's name, verified byte length and SHA-256, and its final location relative to the configured retained root. Receipt lookup uses the pair key; staging invocation names are only scratch identifiers. A receipt need not acquire a separate business identity. Final locations must remain stable, and a receipt never points into staging or back to Tools' input files.

Use private staging directories and a private output subdirectory so output names cannot collide with metadata. Published directories and receipts are immutable to this command. Receipt plus retained bytes are durable evidence; temporary copies and hash accumulators are scratch. There is no independent database, index or journal to keep synchronized.

## One writer across shells

Acquire one nonblocking exclusive OS lock on a stable lock file within the retained root before examining or changing receipt state. Hold it through validation, publication, durable synchronization and receipt readback; release it before writing stdout. A competing shell receives `Busy` and can retry. Use an OS-managed lock whose ownership ends on process exit, not a PID file that requires guessing whether a writer is alive. Never unlink or replace the lock file. Every Assets command that accesses this receipt store must use the same lock protocol; direct external modification is outside the store's supported operation.

The global lock deliberately serializes even unrelated receipts in the first implementation. It needs no pre-existing record store and prevents two shells from publishing different sets under one identity. A later concurrency change must preserve that guarantee; it is not part of this slice.

## Receipt flow and interruption

1. Parse and validate the delivery, construct the canonical expected set, then acquire the lock. Configuration and malformed input failures produce no receipt.
2. If the pair already has a final directory, validate the stored identities, complete set, receipt and retained bytes. A different declared set is `Conflict`; never overwrite the original. A matching declaration permits replay of the existing receipt after retained-byte verification and durable synchronization. Replay acknowledges the already retained, hash-identified set; it does not claim to have ingested a newly modified source file whose manifest still describes the old bytes. A caller delivering changed bytes must supply their actual hashes, which conflict under this key. If existing retained evidence is missing or corrupt, return `ReceiptUnavailable`, preserve it and require recovery investigation; never manufacture success or silently replace it from a retry.
3. Otherwise create a unique private staging directory on the retained filesystem. Open each source safely, copy its contents, and verify the copied file's byte length and SHA-256 against the complete expected set. Hash the retained copy, not only a source read performed earlier. Missing, unreadable, truncated or mismatched bytes are `DeliveryFailure`. A source change during copying is harmless only if the actual retained bytes still satisfy the declaration. No partial set can produce a receipt.
4. Write the final receipt into staging using its final retained locations. Synchronize all output files and the receipt, followed by their containing directories. Once staging is complete, atomically rename the whole directory to its final key without replacing an existing directory. Staging and destination must share a filesystem. The rename publishes bytes and metadata together; synchronize every parent directory affected by the rename before completion.
5. Read back and validate the final receipt, then return its exact saved content. The authoritative completed state is a complete final directory whose files and directory entries have been successfully synchronized. Only then may the command acknowledge receipt. A failed synchronization yields `StorageFailure`, without a success acknowledgement, even if a final directory is visible.

Before publication, interruption leaves no completed receipt. Ignore abandoned staging on the next invocation, re-read Tools' still-retained inputs, and create a fresh staging directory. The first implementation does not automatically delete scratch, original inputs or published output. Scratch reclamation can follow a separately stated policy; deleting retained candidates also requires the handoff's retention policy and retained evidence.

An interruption after rename but before successful synchronization is indeterminate to the interrupted caller. On the next invocation, the same lock protects recovery: if a complete valid final directory exists, verify and synchronize it before replaying the saved receipt. If none exists, retry from inputs. A partial or corrupt final directory is an integrity failure requiring investigation, not permission to acknowledge or overwrite. The supported filesystem must make the rename atomic; how power loss interacts with synchronization needs an actual runtime/filesystem test.

After durable completion, loss of the acknowledgement response leaves the saved receipt and bytes intact. Tools can repeat the same key and canonical set and receive the existing receipt, even if the source location has since become unavailable. Tools retains transfer responsibility until it obtains verified receipt or explicit disposition. Custody does not establish creative acceptance or a selected revision, and receipt alone authorizes no cleanup.

## Cases and evidence

The supplied [delivery](delivery.json) describes `candidate-01` / `attempt-01` with `shape.bin` (24 bytes) and `surface.bin` (26 bytes). A read-only check of the supplied files found both lengths and SHA-256 values match the declarations. This establishes only consistency of synthetic inputs.

For a successful design trace, the command stages both files, verifies them, writes the receipt, synchronizes, publishes the directory, synchronizes its parent and returns the stored receipt. A second matching invocation returns that same receipt. Changing one declared hash, length, output name or set membership under the pair gives `Conflict`; a new attempt has a distinct pair and no implied review or revision status.

If `surface.bin` is missing or fails verification after `shape.bin` has copied, there is no final receipt and the command returns `DeliveryFailure`. If the process exits at that point, a retry starts again from inputs. If it exits after final publication but before replying, the retry verifies the retained set, completes any required synchronization and returns the saved receipt. With two competing shells, one holds the lock; the other receives `Busy`, and after retry either replays the receipt or conflicts with it.

## Smallest next implementation

Choose a language/runtime supporting the stated filesystem primitives, confirm the pair-key interpretation and configure real local input/retained roots. Implement one command, one receipt operation and the filesystem collaborator with no additional storage service. Support only the supplied local manifest form and this one-set transaction. Make the stored receipt versioned and define stable nonzero outcome codes for malformed input, `Busy`, `Conflict`, `DeliveryFailure`, `StorageFailure` and `ReceiptUnavailable`.

Verify the consequential promises through temporary-directory integration checks: a valid two-file receipt; missing and mismatched bytes; safe path rejection; a reordered or relocated identical replay; changed membership and hashes under the same key; and corrupt retained evidence. Run two real processes to prove lock exclusion and process-exit lock release. Inject interruption before publication, after rename, after parent synchronization and during acknowledgement writing, then rerun the command and inspect the actual complete set and saved receipt. Inject synchronization errors to establish that they cannot yield success. A fake storage dependency may test the operation's decisions, but only real filesystem/process checks can establish locking and publication behavior. Host power-loss durability remains unverified until tested on the selected filesystem.

No language-specific, runtime-specific or testing guidance package is installed in this fixture, so implementation-specific guidance and checks remain pending. The design traces are proposals, not evidence that this command works.
