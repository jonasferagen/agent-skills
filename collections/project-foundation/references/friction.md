# Discover and repair guidance problems during work

Use this reference when actual execution exposes missed necessary guidance,
unnecessary reading, misleading or conflicting instructions, repeated
clarification, awkward tooling, duplicated edits or an undocumented workaround.
Routine successful work needs no capture pass or “no friction” report. Discovery
happens within the current task; it does not start a watcher or unattended job.

## Surface the problem and keep work moving

If the problem affects the task's route, correctness, scope or completion, explain
it promptly with its consequence and available workaround. Record minor costs at
a natural checkpoint. Continue unaffected authorized work; stop only the affected
path when required guidance or authority cannot be established. Do not guess a
missing obligation to keep that path moving.

Capture the observation in existing experiment or work notes. Include enough to
reproduce it: the task, installed revision when known, relevant entrypoint and
reads, guidance missed or unnecessary work, consequence, and workaround or open
question. Keep private input out of examples. Create a small friction note only
when no suitable record exists. Reuse an existing finding for the same mechanism,
route and revision; add new evidence rather than duplicating the report.

Separate observation, diagnosis and proposed repair. A missing project decision
belongs to its project owner; missing proof belongs to verification work. Neither
alone establishes a skill defect. A necessary question omitted by guidance can
be a defect when the concrete missed case has a consequence; absence of a topic
heading alone is insufficient. Avoid logging ordinary choices without a concrete
cost or mistake. Fix clear, in-scope project problems within the original task's
authorization; keep uncertain generalizations as candidates.

## Repair demonstrated defects at their source

For a concrete guidance issue, locate the authoring home through project
instructions or installed provenance. Check whether the relevant guidance already
covers the case or a newer source revision already fixes it. Distinguish a source
defect from an outdated installation or a broken project route. Provenance is not
a reading prerequisite for ordinary capture.

User or project instructions may give standing authorization for narrow source
repairs. When that authorization covers the defect, make the smallest useful
correction and its checks without asking again. Follow the source repository's
instructions and worktree rules. This collection does not itself authorize edits
to another repository. If source maintenance is outside scope or unavailable,
retain the concrete candidate, proposed home and validation still needed.

Default to repair after completing the original task, before its final hand-back.
When delegation is available and authorized, an independent subagent may prepare
the repair in an isolated source worktree while useful work continues. Give it
the reproducer, revision, scope and expected checks; avoid overlapping writers.
The main agent checks its result before adopting it. Resolve a blocking defect
before resuming the dependent path. Pending work remains an explicit follow-up;
do not promise execution after the current run ends.

Reproduce the failing route and show that the correction addresses it while
preserving required behavior. Follow the source's checks, including the original
case, a nearby case that should avoid the route and a case requiring deeper
guidance as relevant. Package or link validation alone does not prove routing
quality, and fewer reads do not prove that obligations were preserved.

Keep the repair bounded to the demonstrated mechanism. Leave uncertain
generalizations or a broader redesign as candidates. Do not reorganize the skill
library for each inconvenience or rerun maintenance for the same finding. Capture
a distinct demonstrated defect in this workflow separately; do not recursively
spawn repairs. When a reusable lesson needs further assessment, use pattern-capture
if available; installing it is not required for this workflow.

## Keep repair and adoption distinct

Correct the source rather than independently editing vendored files. A source
repair does not change a consumer's pin. Update an installation only when that
adoption is also authorized, using the complete collection and its provenance
through [installation guidance](installation.md). Do not automatically upgrade
other consumers.

In the hand-back, report material friction, the original task's outcome, whether
the repair is a candidate, applied or checked, what was actually verified, and
whether the consumer adopted it. Retain unresolved evidence or scope limits with
the finding. Ordinary successful work needs no maintenance summary.
